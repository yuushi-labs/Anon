<br/>

>The following are alternative approaches to this PR:

<details>
<summary><b>1. Derive native dev host from Expo hostUri (no hard-coded mDNS)</b></summary>

<dl>
<dd>

- ➕ Avoids hard-coding &quot;anon.local&quot; and works on more LAN setups
- ➕ Can auto-map Metro host (8081) to API port (3000) similarly to web logic
- ➕ Reduces reliance on mDNS configuration on devices
- ➖ Requires additional Expo runtime dependency/logic (e.g., expo-constants)
- ➖ HostUri formats can vary across Expo Go/dev-client modes and tunnels

</dd>
</dl>

</details>

<details>
<summary><b>2. Fail fast on native when API base URL is missing (all non-web)</b></summary>

<dl>
<dd>

- ➕ Prevents silent relative-URL failures that manifest as &quot;network request failed&quot;
- ➕ Forces correct configuration in preview/production builds
- ➖ Less forgiving for ad-hoc internal previews unless a default is provided
- ➖ Requires clear developer documentation for setting EXPO_PUBLIC_API_BASE_URL

</dd>
</dl>

</details>

<details>
<summary><b>3. Support multiple native dev fallbacks (mDNS + adb reverse + LAN IP)</b></summary>

<dl>
<dd>

- ➕ More robust across Android emulators, physical devices, and CI/dev environments
- ➕ Can reduce setup friction for contributors
- ➖ Adds branching complexity and more surface area to test
- ➖ May still be ambiguous which host should be preferred without explicit config

</dd>
</dl>

</details>

>**Recommendation:** The PR’s direction—centralizing URL resolution in getApiBaseUrl() and removing scattered call-site fallbacks—is the right approach. As a follow-up, consider (1) deriving the native dev host from Expo’s hostUri (or similar) to avoid a hard-coded mDNS name, and (2) ensuring native non-dev builds truly fail fast when EXPO_PUBLIC_API_BASE_URL is missing (the current early `return &quot;&quot;` path can bypass the later throw), so preview/production don’t silently fall back to relative URLs.

</dd>
</dl>

</details>
